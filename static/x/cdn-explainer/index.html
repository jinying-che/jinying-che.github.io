HTTP → CDN · 图解指南

看懂 CDN，从一条请求开始。

CDN 把入口放到用户附近；能安全复用的响应，就在边缘直接返回。源站仍负责生成内容。

整体架构请求流程缓存更新配置要点
01

CDN 到底部署在哪里？

典型的反向代理 CDN：多个边缘节点连接同一组源站，而不是把整个应用复制到每座城市。

两段 HTTPS：浏览器 ↔ 边缘，边缘 ↔ 源站。边缘通常终止浏览器 TLS；回源也应启用 HTTPS 并验证源站证书。命中可省掉回源延迟和负载，未命中不保证更快。
02

一条请求，如何决定走哪条路？

假设浏览器自己的缓存未命中，请求已到达边缘。下面先判断能否共享，再判断缓存是否可复用。

缓存键 Cache key决定“谁能共享”。常见组成是主机名、路径、查询参数；语言、编码等变体也要正确区分。Cookie 并不自动代表不能缓存。
TTL决定“多久算新鲜”。有效期内可以复用，不保证一直驻留：缓存仍可能被提前淘汰。各厂商对 Vary 和缓存键的支持不同。
03

内容变了，缓存怎么办？

源站可能如何回答？

304 Not Modified
内容未变：更新缓存元数据，再把已有内容返回用户。

200 OK + body
内容已变：返回新内容；符合缓存规则时替换副本。无验证器时通常直接取完整响应。

如果允许 stale-while-revalidate，可先返回旧内容并后台刷新；故障时是否允许旧内容，也取决于策略。

主动更新：版本化 URL 最容易推理

04

记住这些规则，就够开始了。

版本化静态文件

图片、CSS、JS：内容变更就换 URL，通常适合长 TTL。

公共 HTML / API

相同响应供多人使用时可缓存；用短 TTL 或验证，明确可接受的过期时间。

个人数据

账户、购物车等应明确绕过共享缓存；检查 CDN 规则不会覆盖隐私策略。

Cache-Control: public, max-age=60, s-maxage=600
ETag: "v1"

在响应可缓存且无覆盖规则时：浏览器新鲜期 60 秒，共享缓存 600 秒；响应已有的 Age 计入有效期。

private仅私人缓存（如浏览器）可存储，共享缓存不可存储。
no-storeHTTP 缓存不应存储这份响应。
no-cache可以存，但复用前必须成功验证。
public允许共享缓存；不保证 CDN 实际会缓存。
怎么确认真的命中？

查看 Cache-Control、Age（如有）和厂商状态头，例如 Cloudflare 的 CF-Cache-Status。重复请求仍可能未命中；同时观察延迟、命中率和源站流量。

有 CDN，源站就不会挂？

缓存可吸收部分流量，策略也可能允许故障时返回旧内容。但未缓存内容、写入与依赖源站的 API 仍会失败；CDN 不能替代源站容灾。

Cloudflare 就是 CDN 吗？

CDN 只是其中一部分；安全过滤与边缘计算是不同能力。流量经过 Cloudflare 不代表缓存命中，默认规则也不缓存 HTML / JSON，具体以配置为准。

HTTP → CDN · A VISUAL GUIDE

CDNs, one request at a time.

A CDN puts a front door near users. When a response is safe to reuse, the edge answers directly. Your origin still produces the content.

ArchitectureRequest flowCache updatesPractical rules
01

Where does a CDN sit?

A typical reverse-proxy CDN has many edge locations backed by your origin infrastructure. It does not copy your whole application into every city.

Two HTTPS legs: browser ↔ edge, then edge ↔ origin. The edge usually terminates browser TLS; also enable HTTPS and certificate validation to origin. Hits save origin latency and load; misses are not guaranteed to be faster.
02

Which path does a request take?

Assume the browser’s own cache did not answer and the request reached the edge. First check sharing policy, then whether a cached copy can be reused.

Cache keyDefines who can share: commonly hostname, path and query parameters. Distinguish language / encoding variants too. A cookie does not automatically prevent caching.
TTLDefines freshness lifetime, not guaranteed residency: an entry can be evicted early. Support for Vary and custom cache keys differs by provider.
03

What happens when content changes?

What can the origin return?

304 Not Modified
Unchanged: refresh metadata, then serve the stored body.

200 OK + body
Changed: return the new body and replace the cached copy if eligible. Without a validator, normally fetch the full response.

If stale-while-revalidate is allowed, serve the old response while refreshing in the background. Serving stale content on errors also depends on policy.

Publishing changes: versioned URLs are easier to reason about

04

The rules you need to get started.

Versioned assets

Images, CSS and JS: change the URL when bytes change; usually suitable for long TTLs.

Public HTML / APIs

Cache when many users share the same result. Use short TTLs or validation with an explicit freshness budget.

Personal data

Explicitly bypass shared caches for accounts and carts. Check CDN overrides do not defeat privacy policy.

Cache-Control: public, max-age=60, s-maxage=600
ETag: "v1"

For an eligible response without overriding rules: 60 seconds of freshness in a browser, 600 in a shared cache. Existing response age counts toward that lifetime.

privatePrivate caches such as browsers may store it; shared caches must not.
no-storeHTTP caches must not store this response.
no-cacheStorage is allowed, but reuse requires successful validation.
publicAllows shared caching; does not guarantee the CDN will cache it.
How do I confirm a cache hit?

Inspect Cache-Control, Age when present, and vendor headers such as Cloudflare’s CF-Cache-Status. Repeated requests may still miss. Measure latency, hit ratio and origin traffic together.

Does a CDN eliminate origin outages?

Caches absorb some traffic and may serve stale responses if allowed. Uncached content, writes and origin-dependent APIs can still fail. A CDN does not replace origin resilience.

Is Cloudflare just a CDN?

CDN delivery is one capability; security filtering and edge compute are separate. Traffic passing through Cloudflare is not necessarily a cache hit. Default rules do not cache HTML / JSON; effective configuration matters.
