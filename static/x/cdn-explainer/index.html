01 / A shared front door

Your origin still owns the content.

Without a CDN, a browser connects to your server, which we’ll call the origin. With a CDN configured for that hostname, the browser connects to a server in the CDN’s network. This server is an edge: a reverse proxy that can fetch from your origin and may keep reusable responses.

Origin

Your application or storage service. It produces the authoritative HTML, images, API responses, and other content.

Edge / PoP

A CDN location near users in network terms. A point of presence (PoP) contains infrastructure serving a region; it is not a copy of your whole application.

Cache

Stored responses plus rules for reuse. A fresh, matching response can answer many users without asking the origin again.

Why this helps: a reusable response avoids a longer trip to the origin and work on that server. A CDN can also absorb traffic spikes. A cache miss still needs the origin and may add overhead; faster delivery is not automatic for every request.

02 / Follow the bytes

Same URL. Different journeys.

  1. Find the front door. DNS resolves your hostname to CDN infrastructure. Depending on the provider, DNS steering and/or anycast routing select an edge. “Nearest” means a network routing choice, not necessarily the closest city.
  2. Connect securely. The browser establishes HTTPS with the edge. For a typical reverse-proxy CDN, the edge terminates TLS; it uses a separate connection to the origin. Configure HTTPS and certificate validation on that leg too.
  3. Decide whether to reuse. The edge checks cache eligibility, a matching cache key, and freshness. If it cannot reuse a response, it fetches or validates with the origin.
  4. Return the response. The browser receives ordinary HTTP. It can apply its own caching policy independently.

MISS · No stored copy

Browser → edge → origin → edge → browser

This edge does not have the image. It fetches the origin’s response, forwards it to the browser, and stores a copy if the response is eligible. Another edge may still be cold.

Origin work: yes. The first visitor often pays the cost of filling the cache.

HIT / MISS

A hit uses a fresh matching copy at the edge; no origin request is needed. A miss fetches the content and may store it. Caches are not necessarily populated globally at once.

STALE / BYPASS

An expired copy can be revalidated: an ETag sent in If-None-Match lets the origin return 304 Not Modified, or a new 200 body. A bypass goes to origin because policy says not to reuse a shared copy.

These names describe concepts; provider status labels differ. With an allowed stale-serving policy, a CDN may serve an old response while refreshing it or during an origin error. That behavior must be configured and bounded.

03 / Correctness before speed

Two questions control every cache hit.

1. Is this the same representation?

A cache key identifies which requests may share a response. It commonly includes the hostname, path, and query string, with provider-specific options for headers and cookies. /photo.jpg?size=small and /photo.jpg?size=large must not collide if they produce different images.

If responses vary by language or encoding, configure the CDN to distinguish those representations. HTTP’s Vary expresses that distinction, but supported fields and custom cache-key behavior depend on the provider. Never assume a cookie automatically prevents caching.

2. Is this copy still allowed to be reused?

TTL means time to live: the freshness lifetime of a cached response. It is permission to reuse a response for a period, not a promise that it stays in memory; an edge can evict a fresh entry sooner.

HTTP/1.1 200 OK
Cache-Control: public, max-age=60, s-maxage=600
ETag: "image-v1"

For an eligible response under normal HTTP caching semantics, the browser gets a 60-second freshness lifetime; a shared cache gets 600 seconds. A response’s existing age counts toward that lifetime. CDN rules can change the effective policy, so check the actual configuration.

Useful response directives and what they mean
DirectiveMeaning
publicAllows shared caching; does not by itself guarantee a CDN will cache the response.
privateFor a private cache, such as the user’s browser; shared caches must not store it.
no-storeDo not store this response in an HTTP cache.
no-cacheStorage is allowed, but reuse requires successful validation. It does not mean “never store.”
s-maxageSets freshness for shared caches, overriding max-age there.

The serious failure mode is sharing the wrong response. A user’s account page must not become another user’s cache hit. Use explicit private/no-store policies as appropriate, bypass shared caching for authenticated routes, and verify that CDN overrides do not undo that policy.

04 / Make it useful

Choose policy by content.

Versioned assets

Images, CSS, and JavaScript with content-specific filenames can use long TTLs. Publish app.a7c3.js as a new URL when bytes change; keep old assets available for existing pages.

Public HTML / data

Cache when many users receive the same result and some delay is acceptable. Use shorter TTLs or revalidation. Dynamic generation does not inherently make a response uncacheable.

Personal data

Account pages, carts, and private API responses need explicit handling. Start with shared-cache bypass; only add caching after proving who can reuse which response.

“I changed the origin. Why is the old page still there?”

The edge may still have a fresh copy. You can wait for expiry, purge the CDN entry, or publish a new versioned URL. A purge removes CDN copies according to the provider’s scope and propagation behavior; it does not erase a copy already fresh in someone’s browser.

Inspect a real response

curl -sS -D - -o /dev/null https://your-domain.example/image.jpg

Replace the example hostname and path with a resource you control. Run it twice. Inspect Cache-Control, Age if present, and the provider’s cache-status header. Cloudflare exposes CF-Cache-Status. A repeated request is not guaranteed to hit: eligibility, routing, expiry, and eviction can change the result.

Measure cache-hit ratio alongside latency and origin traffic. Request hit ratio is hits divided by requests in the population you chose; byte hit ratio measures bytes instead. State whether bypassed requests are included. A high hit ratio alone does not prove that personalized pages are fast or correct.

Does a CDN keep my site online if the origin fails?

It may continue serving reusable cached responses or allowed stale content. Uncached pages, writes, and origin-dependent APIs can still fail. A CDN is not a replacement for origin resilience.

Does every request need to be cacheable?

No. A CDN can proxy an uncached request and provide TLS handling, filtering, connection reuse, or routing improvements. It still needs the origin to produce that response unless you explicitly run application logic at the edge.

What does it cost?

Caching can reduce origin bandwidth and compute, but CDN requests, traffic, logs, or edge execution may carry charges. Provider pricing and the traffic pattern determine the total; a CDN is not automatically cheaper.

05 / Connect it to Cloudflare

The CDN is one part of the platform.

You mentioned the Cloudflare / NET investment page. Use this explainer as the technical foundation for thinking about a CDN business. That page could not be retrieved while preparing this draft, so its specific arguments are not summarized here.

Distinguish three jobs: delivery moves and caches content; security filters traffic; edge compute executes code. They can share infrastructure, but enabling one does not mean every capability is active.

For Cloudflare specifically, proxying a hostname does not mean all its responses are cached. Its documented defaults do not cache HTML or JSON; cache rules can change eligibility. Always distinguish “traffic passes through Cloudflare” from “this response was a cache hit.”

What to remember: a CDN is a distributed HTTP intermediary. Its most useful shortcut is serving a nearby, correct, reusable response. The origin remains involved whenever that shortcut is unavailable.
